# SoftCode Landing Page High-Level Design

## 1. Document Purpose

This document defines the high-level design for the SoftCode company landing page.
The landing page is intended to be a concise, professional web presence for a small full-stack development team that helps small businesses and local startups design, build, and launch web solutions.

The document is written in English, but the website itself must use Ukrainian for all user-facing content.

## 2. Product Overview

SoftCode is a small dedicated development team focused on practical digital solutions for small businesses and early-stage startups. The company provides design, frontend development, backend development, full-stack web application development, process automation, and integrations with external APIs and services.

The landing page should present SoftCode as a friendly, capable, and approachable freelance-style technology team. The tone should avoid exaggerated agency claims and instead communicate reliability, clear communication, and the ability to deliver useful solutions based on the client's budget and business needs. The company can also mention practical server-side support capabilities, including Linux server management, deployment assistance, and basic operations support.

## 3. Goals

The primary goals of the landing page are:

- Generate project requests from potential clients.
- Present SoftCode's services clearly and professionally.
- Explain that the team can handle both simple landing pages and larger full-stack projects.
- Build trust by showing the team's roles, commercial experience, and company contacts.
- Provide an easy contact form that sends project requests to the company email.

## 4. Non-Goals

The first version of the landing page should not:

- Become a large multi-page corporate website.
- Include complex account functionality, dashboards, or client portals.
- Present SoftCode as a large enterprise agency.
- Depend on a heavy portfolio section if real client work cannot be disclosed.
- Use English, Russian, or any other non-Ukrainian language in the live website UI.

## 5. Target Audience

The landing page is targeted at:

- Small businesses that need a website, landing page, automation, or custom web application.
- Local startups that need MVP development or technical support from idea to launch.
- Business owners who have a project idea but need help clarifying scope, budget, and implementation steps.
- Clients who prefer a small dedicated team instead of a large agency.

The website should be understandable for non-technical clients while still showing enough technical credibility.

## 6. Brand and Positioning

### Brand Name

The public brand name on the website should be `SoftCode`.

### Suggested Positioning

SoftCode should be positioned as:

- A small dedicated team.
- A practical web development partner for small businesses and startups.
- A team with commercial enterprise experience.
- A team that can support projects from idea and design through development, launch, and further improvement.

### Tone of Voice

The website tone should be:

- Friendly.
- Clear.
- Startup-like.
- Practical.
- Professional without sounding corporate or inflated.

All text must be written in Ukrainian.

## 7. Language Requirements

The website must support one language only: Ukrainian.

This applies to:

- Navigation labels.
- Section headings.
- Body text.
- Buttons and calls to action.
- Contact form labels.
- Contact form placeholders.
- Validation messages.
- Success and error messages.
- SEO title and meta description.
- Open Graph and social preview text.
- Image alternative text.
- Cookie, privacy, or legal notices if they are added later.

No user-facing English text should appear on the landing page, even when describing technologies or services. Technology names such as `Java`, `Spring`, `Angular`, `Docker`, `Bootstrap`, `C++`, and `C#` may remain in their original technical form.

Common product and technology abbreviations such as `CRM`, `MVP`, `SPA`, `API`, and `web application` may be used only when they are useful for clarity. When such terms appear in user-facing content, the Ukrainian copy should explain their practical meaning for the client in simple business language.

### 9.6 Process Section

The process should be simple and understandable.

Recommended steps:

1. Discovery: understand the client's business goal, users, scope, and constraints.
2. Planning: define the project structure, priorities, budget range, and timeline.
3. Design: create visual direction, UI layouts, or a lightweight prototype where needed.
4. Development: implement frontend, backend, integrations, and responsive UI.
5. Review and testing: verify the result on key devices and fix issues.
6. Launch: deploy the solution and support the first release.

The process should be presented visually as a compact stepper or timeline.

### Form Submission

The form should send requests to:

- softcodetechnologies582@gmail.com

Possible implementation options:

1. Use a form delivery service such as Formspree, Getform, or EmailJS.
2. Implement a backend endpoint that receives form data and sends email.
3. Use a temporary `mailto:` fallback only if the team wants the simplest possible first release.

Recommended first-release approach:

- Protect the form against spam using a lightweight anti-spam mechanism such as honeypot field, rate limiting, or a provider-level spam filter.

## 11. UX Requirements

The landing page should:

- Be easy to scan.
- Work well on mobile, tablet, and desktop.
- Keep sections concise.
- Use clear section hierarchy.
- Include visible calls to action near the top and near the bottom.
- Avoid unnecessary animations or heavy visual effects.
- Make the contact form easy to complete.
- Clearly show that SoftCode works with different project sizes and budgets.

## 12. Visual Design Direction

The design should feel:

- Modern.
- Clean.
- Friendly.
- Trustworthy.
- Lightweight.
- Suitable for a small software team.

The design should avoid:

- Overly corporate visuals.
- Excessive gradients.
- Generic stock-photo-heavy composition.
- Large agency-style claims.
- Visual clutter.

Recommended visual approach:

- Simple professional layout.
- Strong typography.
- Restrained color palette.
- Clear cards or blocks for services and project types.
- Subtle icons for service categories.
- Compact team cards.
- A visible but not oversized contact form.

No exact color palette is defined yet. The implementation team may choose a clean palette during UI design.

## 13. Technical Architecture

### Frontend

The landing page should be implemented as an Angular application.

Current project baseline:

- Angular 21.
- TypeScript.
- Angular CLI build setup.
- Vitest available for tests.

Planned frontend additions:

- Bootstrap as the required layout and responsive UI framework for this application.
- Angular Material for selected UI controls if needed.
- SCSS for styling.

The implementation should use Angular components for major sections:

- Header component.
- Hero component.
- Services component.
- Project types component.
- Why SoftCode component.
- Process component.
- Team component.
- Contact form component.
- Footer component.

For a simple first release, these may also be implemented within a smaller component structure if the code stays maintainable.

### Backend or Form Delivery

The first version of the landing page should be a static Angular SPA and should not require a custom backend. The only backend-like requirement is contact form delivery.

Preferred options:

- External form delivery service for faster launch.
- Lightweight backend endpoint for better control.

If a backend is implemented, the likely backend stack can include:

- Java.
- Spring.
- Email delivery integration.
- Basic spam protection.

Backend implementation is not part of the recommended first-release landing page scope.

### Deployment

The recommended first-release deployment target is GitHub Pages or equivalent static hosting that supports Angular SPA deployment.

Recommended deployment characteristics:

- Static hosting for Angular build output.
- SPA routing support using GitHub Pages-compatible fallback behavior.
- No dedicated backend server for the landing page.
- Optional future VPS, Linux server, or Docker-based deployment if the product scope grows beyond a static landing page.

## 15. Accessibility Requirements

The landing page should:

- Use semantic HTML.
- Provide accessible labels for all form inputs.
- Provide useful alt text for meaningful images.
- Maintain sufficient color contrast.
- Support keyboard navigation.
- Avoid hover-only access to important information.
- Provide visible focus states.
- Use readable font sizes on mobile and desktop.
- Show form errors in a way that screen readers can understand.

## 16. Performance Requirements

The first release should:

- Load quickly on mobile connections.
- Avoid unnecessary large dependencies.
- Optimize images and icons.
- Lazy-load non-critical assets where reasonable.
- Keep animations lightweight.
- Avoid blocking third-party scripts where possible.

## 17. Content Requirements

All production content should be written in Ukrainian.

Required content:

- Clear hero message.
- Service descriptions.
- Project type descriptions in Ukrainian.
- Team section.
- Contact form labels and validation messages.
- Footer text.

Content should be concise and practical. It should not overpromise results, team size, or client outcomes. Project examples, service descriptions, technology explanations, and portfolio-like blocks must be authored in Ukrainian and written for non-technical clients.
